## Design and Architecture

### DA-001 [MINOR]
Location: `CLAUDE.md:303-309` (Untrusted Input section) vs. `.claude/agents/hve-pr-reviewer.md:23`, `.claude/agents/hve-researcher.md:49`
Finding: The new canonical `## Untrusted Input` section states that three categories of content are untrusted: "Diff content, fetched web content, and file content under review." Only two of those three categories are actually wired to a pointer — `hve-pr-reviewer.md:23` covers diff content and `hve-researcher.md:49` covers fetched web content. No agent references the section for "file content under review," even though `hve-implementation-validator.md` (reads modified files as evidence for 11 quality dimensions), `hve-rpi-validator.md`, and `hve-plan-validator.md` all read file content that literally fits that phrase. The original 2026-08-10 review's SC-04/SC-05 findings (`.claude-hve-tracking/reviews/pr/main/2026-08-10-full-repo-review.md:206-214`) deliberately scoped the guard to just the two most externally-exposed agents on a documented blast-radius argument, so the narrow wiring is a defensible, faithful implementation of that finding — but the canonical text in `CLAUDE.md` now describes a broader scope than what it's connected to. A contributor who reads only `CLAUDE.md` would reasonably expect the validators to carry the same pointer; there is nothing (test 14 only checks that existing pointers resolve, it does not check that applicable consumers carry one) that would catch a future agent reading "file content under review" without ever being told to apply this rule.
Recommendation: Either narrow the `CLAUDE.md` sentence to name only diff content and fetched web content (matching current wiring), or add a short one-line note under the bullet list clarifying that internal file review by the RPI validators is out of scope for this guard and why (mirroring the blast-radius reasoning already in the original review).

### DA-002 [MAJOR]
Location: `README.md:44`, `README.md:247`, `docs/installation.md:26`, `docs/installation.md:90-93`, `docs/installation.md:158`, `docs/installation.md:189-194`, `install.sh:246-251`, `install.sh:268-274`
Finding: This remediation's own stated philosophy (`.claude-hve-tracking/plans/2026-08-15/full-repo-review-remediation-plan.md:12`) is that "the systemic text-duplication cluster (RL) lands at Phase 5 so every later phase edits a reduced surface," and Phase 5 spent real effort collapsing duplicated prose in `.claude/` into single `CLAUDE.md` carriers with drift-test guardrails (`tests/run-drift-tests.sh:562-579`, `CANONICAL_BLOCK_SPECS`). Phase 11 (documentation sync) then did the opposite for the six-pattern credential list (`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`): it added the literal list to `README.md` in two places and to `docs/installation.md` in four places, on top of the two copies already in `install.sh` (the `add_ignore` calls and the global-mode echo block). Counting the canonical `CLAUDE.md:295` bullet, `tests/run-drift-tests.sh:291`, and `tests/run-install-tests.sh:515`, the same list is now spelled out independently in at least 11 places across the repo. `canonical_block_corpus()` (`tests/run-drift-tests.sh:582-589`) — the mechanism Phase 5 built to prevent exactly this class of silent drift — only scans `.claude/commands/*.md`, `.claude/agents/*.md`, `.claude/prompts/*.md`, and `CLAUDE.md`; it does not cover `README.md` or `docs/`. The changes log itself flags one instance of this gap (`docs/internals.md` not being in the corpus, `.claude-hve-tracking/changes/2026-08-15/full-repo-review-remediation-changes.md:841-845`) but the much larger new-duplication surface this same phase created in `README.md` and `docs/installation.md` was not raised. The one-time by-execution verification in the changes log (Phase 11 and the Post-Review Remediation section) confirms the copies agree today, but nothing prevents them from silently diverging on the next edit to any one of them.
Recommendation: Extend `canonical_block_corpus()` (or add a parallel, lighter-weight check) to include `README.md` and `docs/*.md`, at minimum for the credential-pattern list, so a future edit to one copy that isn't mirrored everywhere fails the suite instead of relying on a point-in-time manual verification.

### DA-003 [MINOR]
Location: `.claude/agents/hve-implementation-validator.md:112` vs. `.claude/commands/hve-pr-review.md:54`
Finding: Both files were edited in the same phase (Phase 3, DEFECT 1/DEFECT 3) to expose the identical "additive coverage floor" concept in their output templates, but they use different field names for it: the quality-validator log template reads `Scope: [dimensions validated] | Not covered: [dimensions skipped, or \`none\`]`, while the PR-review log template reads `Coverage: [dimensions reviewed] | Not covered: [dimensions skipped, or \`none\`]`. Same idea (which dimensions ran vs. which were intentionally skipped under the additive-scope rule), same `Not covered:` suffix, different label for the first half (`Scope:` vs `Coverage:`). A reader comparing an RPI quality log to a PR review log for the same underlying "was security actually checked" question has to remember two different header names for the same fact.
Recommendation: Pick one label (`Coverage:` reads more naturally alongside "coverage floor," the term used in `CLAUDE.md`'s `Security Hygiene` section) and use it in both templates, or document in `CLAUDE.md` why the two artifact types intentionally use different vocabulary.
