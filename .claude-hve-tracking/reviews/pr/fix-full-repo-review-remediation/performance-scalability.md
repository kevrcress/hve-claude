## Performance and Scalability

### PS-001 [MAJOR]
Location: `.claude/commands/hve-research.md:20` vs `.claude/commands/hve-research.md:38` vs `CLAUDE.md:42-43` vs `.claude/commands/hve.md:39`
Finding: This diff's own fix for PS-01 ("the upper number in that column is the binding cap ... not a suggestion", new text at `hve-research.md:38`, mirrored in the new `CLAUDE.md:43` row: "`lightweight` 1 researcher, `standard` 3, `full` 5") is contradicted by text sitting a few lines away in the same, still-untouched `## Inputs` section:

`hve-research.md:20`: `` Mode: `--mode` overrides the difficulty assessment when explicitly passed (`lightweight` = 1 subagent, `standard` = 2–3, `full` = 3–5). ``

That is a *range* ("standard = 2–3") for the exact flag the new Phase 0 text calls a hard, single-valued cap ("standard 3"). A third value appears in `hve.md:39` (untouched by this diff, but sitting next to Phase 0/1's cap-mapping table this diff also edited): "`standard` | Treat as Medium: run the full RPI loop with 1–2 researcher subagents..." — and `CLAUDE.md:42` (also untouched) repeats that "1–2 researchers" figure for `/hve --mode standard`. So across the four places this diff touched or sits adjacent to, `--mode standard`'s research-subagent count is stated as 3 (new, twice) and as 2–3 or 1–2 (old, twice), left unreconciled. This is precisely the "stated upper bound tied to classification tier, no contradiction" property Phase 8's own success criterion required (`.claude-hve-tracking/plans/2026-08-15/full-repo-review-remediation-plan.md`, Phase 8 criterion, quoted in the changes log as "every fan-out has a stated upper bound ... no two instructions in one file contradict") — and it is not met inside `hve-research.md` itself once line 20 and line 38 are read together.
Recommendation: Update `hve-research.md:20` to state the same fixed caps as line 38 (`lightweight` 1, `standard` 3, `full` 5) and drop the range language, or replace line 20 with a one-line pointer at Phase 0's table so there is exactly one carrier of the number, consistent with this diff's own dedup pattern used elsewhere (RL-03 etc.). Reconcile `hve.md:39` / `CLAUDE.md:42`'s "1–2" figure at the same time — it describes a different cap (the `/hve` orchestrator's Medium-tier mapping) but uses the same words ("researcher subagents") for a different number, which is confusing even if technically a separate flag scope.

### PS-002 [MAJOR]
Location: `.claude/commands/hve-review.md:85,87,99`
Finding: This diff rewrote the PS-03 context-discipline contradiction by declaring "full-text consolidation wins": `hve-review.md:99` now reads "Read every validation output file in full — those artifacts are already condensed, so they are your evidence base, not noise to skim." That line sits directly below an *unbounded* fan-out that this diff did not touch: `hve-review.md:85` still spawns "one `hve-rpi-validator` subagent" for **every** plan phase marked Complete, with no tier cap analogous to the ones this same diff added to `hve-research.md` (PS-01), `hve.md` (PS-02), and `hve-doc-ops.md` (PS-06, capped at 8 with batching). This diff also adds a new line 87 ("Under `--mode full`, dispatch the Phase 3 quality validator in this same Agent batch") that increases the size of that same uncapped batch by one more subagent.

The result: Phase 2's context cost under the new mandatory-full-read rule is O(N) full-text validator reads, N = count of Complete phases, with no upper bound and no batching fallback — unlike every sibling fan-out this remediation pass fixed. This is not a hypothetical: this very branch's own remediation plan (`.claude-hve-tracking/changes/2026-08-15/full-repo-review-remediation-changes.md`) has 11 phases. A `--mode full` `/hve-review` of this branch would, by the rules this diff just wrote, dispatch up to 11 RPI validators plus 1 quality validator in a single Agent batch and then require reading all 12 output files in full (line 99) before Phase 4 can synthesize a verdict — the exact "unbounded spawning/reading" pattern PS-06 and PS-01 were written to prevent elsewhere in this same diff.
Recommendation: Apply the same tier-cap-and-batch pattern used for PS-01/PS-02/PS-06 to the RPI-validator dispatch in `hve-review.md` Phase 2 (e.g., a hard cap with the `hve-doc-ops.md:51` descending-size-batch fallback), or explicitly bound how many full-text validator files the parent holds in context at once (e.g., consolidate in capped batches rather than one all-at-once read). At minimum, note the gap as a known limitation the way PS-07 was graded Minor rather than silently leaving it uncapped while three sibling commands got caps in the same pass.

### PS-003 [MINOR]
Location: `tests/run-drift-tests.sh:564-579,598-610`
Finding: `CANONICAL_BLOCK_SPECS` grew from 11 to 14 rows in this diff (new rows `friction_capture`, `security_checklist`, `shell_stays_in_parent`). `test10_canonical_block_drift` (`tests/run-drift-tests.sh:644-650`) calls `assert_canonical_block` once per row, and each call independently re-walks `canonical_block_corpus()` (`tests/run-drift-tests.sh:582-589`) and runs a fresh `grep -qF` per corpus file (`tests/run-drift-tests.sh:606-610`) — the corpus file list is rebuilt and re-scanned from scratch on every spec, an O(specs × corpus_size) pattern with no caching between iterations. At the current corpus size (~45 files under `.claude/commands`, `.claude/agents`, `.claude/prompts`, plus `CLAUDE.md`) this is a few hundred subprocess `grep` calls and negligible wall-clock time, so it is not a practical problem today. It is worth flagging because this diff is the second consecutive change to grow this table (11→14 rows) without addressing the underlying scan shape, and both `specs` and `corpus_size` grow together as the prompt-engineering surface grows.
Recommendation: no action required at current scale. If `CANONICAL_BLOCK_SPECS` keeps growing, cache the corpus file list once per `test10_canonical_block_drift()` invocation (a single `mapfile` before the spec loop) instead of rebuilding it inside `assert_canonical_block` on every call.
